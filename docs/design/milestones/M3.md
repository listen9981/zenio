# M3 Task 与单线程 Runtime

状态: 已审查 (2026-11-24)
前置条件: M1、M2、R1 已完成

## 1. 目标

让第一批协程跑起来。`Task<T>` 有了完整的实现, `Try` 因此可用; `Builder::CurrentThread()` 能建出运行时, `Runtime::BlockOn` 能运行主任务; 单线程调度循环和上下文传播到位; `Waiter` 的协议部分实现并被单测覆盖。完成后 M1 头文件里的 `Task`、`Try`、`Runtime`、`Builder`、`Handle`、`EnterGuard`、`Yield` 可以真正使用。

设计会话在临时目录里按这套设计搭过一个原型, 下面各节标了"原型验证过"的行为都在 Apple Clang 21 和 Homebrew Clang 23 上跑通了, Debug、Release、ASAN 都试过。原型没有进仓库, 以文档为准。

## 5. 实现要求

### 5.1 签名

公开的签名以 M1 的头文件为准。这次只有两处不同:

- `Handle` 新增 `[[nodiscard]] bool operator==(const Handle& other) const noexcept;` (A21)。
- `Runtime::BlockOn` 的注释多一行 `@throws std::runtime_error`。

其余改动都是私有的: 友元、私有成员、私有函数。逐项列在各文档「相对 M1 的改动」那一段里。

文档里的代码块是完整的, 照抄。`Task<void>`、`Task<T&>` 没有逐行给出的定义, 按 design/task.md 2.4 末尾的规则从主模板得到。

### 5.2 上下文

- 线程局部变量、`CurrentContext`、`SetCurrentContext` 定义在 `context.cpp`, 不写成头文件里的 `inline` 函数加 `static thread_local`。那样写的话, 共享库和使用者程序里会是两份互不相干的变量。原型验证过: 两个函数导出之后, 只包含 `<zenio/zenio.h>` 的程序链接共享库能运行。
- `InitialAwaiter::await_suspend` 不再是空的函数体, 它把句柄记进 `self_`。
- `FinalAwaiter::await_suspend` 返回 `std::coroutine_handle<>`, `Task<T>::Awaiter::await_suspend` 也是。这两个返回类型不要改, 中间也不要插入别的调用: 协程机制靠它们做尾调用 (design/task.md 第 6 节)。
- `Task<T>::Awaiter::await_resume` 先 `SetCurrentContext(saved_)`, 再取产出。取产出会抛异常, 顺序不能反。

### 5.3 `Task`

- 帧只在 `~Task()` 里销毁。`Awaiter::await_resume` 不调用 `destroy()` (A17)。
- `Task<void>` 的成员函数定义要加 `inline`。
- 三个断言照文档写: `await_ready` 里检查句柄非空; `await_suspend` 里检查还没有等待方; `~Task()` 里检查协程没在运行。原型验证过后两个: 误用时确实中止进程。
- `TaskAccess` 只有 `Runtime::BlockOn` 用。协程体里要等另一个任务, 一律 `co_await`。

### 5.4 导出 (S31)

- 导出的 `zenio::detail` 符号恰好是三个: `CurrentContext`、`SetCurrentContext`、`YieldAwaiter::await_suspend`。前两个标在函数声明上, 第三个靠 `YieldAwaiter` 类上的 `ZENIO_EXPORT`。
- 每个 `.cpp` 的第一个 include 是声明它所定义的东西的头文件。`Yield()` 声明在 `task.h`, 定义放进 `task.cpp`。放错文件不会报编译错误, 但共享库里会缺这个符号, 见 design/build.md 第 6 节。
- 其余 `zenio::detail` 里的东西都不导出: `Scheduler`、`Runnable`、`ScopedContext`、`Waiter`、`RuntimeCore`、`RuntimeOptions`、`TaskAccess`、`TakeTaskResult`、`InitialAwaiter`、`FinalAwaiter`。单测能用它们, 靠的是直接链接目标文件 (S28)。

### 5.5 调度器与 RuntimeCore

- `Scheduler::RunOne` 先把 `Runnable` 拷出来、从队列里弹掉, 再恢复协程 (design/scheduler.md 4.3)。
- 恢复协程的前后用 `ScopedContext` 装上和还原上下文。
- `RuntimeCore::RunRoot` 的进入检查、`FlagGuard`、投递时用根上下文, 照 design/runtime.md 4.2。
- 根任务的 `Runnable` 里, `context` 是 `&root_context_`, 不是根任务自己的 promise。单元测试里直接驱动调度器、投递没启动过的 `Task` 时也一样。

### 5.6 `Runtime`

- `Runtime::BlockOn` 是模板, 定义在 `runtime.h` 里; 其余在非模板的 `Runtime::RunRoot` 里。
- `Builder::Build()` 在 `workers_ != 0` 时抛 `std::runtime_error`, 文本写明是 M6 的事。M6 实现时删掉这个分支。
- `Builder::MultiThread(n)` 在 n 小于 1 时抛 `std::invalid_argument`。
- `~Runtime()` 在 M3 就是 `= default`。
- `EnterGuard` 的 `Reset()` 只在 `active_` 为 true 时还原。

### 5.7 单元测试

通则:

- 用 GTest, 文件名以 `_unittest.cpp` 结尾。测试文件可以包含内部头 (`zenio/detail/...`) 和平台头。
- 用例覆盖 design/task.md 第 7 节、design/runtime.md 第 7 节、design/scheduler.md 第 7 节、design/waiter.md 第 7 节里标了 M3 的每一条, 加上下面的 `Try` 用例。每条至少一个 `TEST`。
- 需要直接驱动调度器的测试 (`scheduler_unittest`、`waiter_unittest`) 自己构造 `RuntimeCore`: `std::make_shared<zenio::detail::RuntimeCore>(zenio::detail::RuntimeOptions{})`。取 `Task` 的句柄用 `zenio::detail::TaskAccess::Handle`。
- **测试里的协程函数一律写成普通的命名函数, 不写带捕获的 lambda** (design/task.md 第 6 节)。状态用指针或引用通过参数传进去。
- **协程函数的函数体里必须有 `co_await`、`co_return` 之一**。原型的测试代码有两次漏了 `co_return;`, 函数就不是协程, `-O0` 下碰巧能跑, `-O2` 下读到垃圾。编译时 `-Wreturn-type` 的警告就是这种错。

`task_unittest.cpp` 里的嵌套测试:

- 10 万层嵌套和 10 万层深处抛异常的两个用例, 在一个栈只有 512 KB 的线程上跑。原因见 design/task.md 第 6 节的表: Release 构建下即使交接写坏了, 10 万层也只占 3 MB, 在主线程的栈上溢不出来; 512 KB 的栈上, 每层 31 字节也要 3 MB。
- 用 `pthread_attr_setstacksize` 设栈大小, `pthread_create` 起线程。线程函数里不写 GTest 的断言, 把结果记进一个结构体, `join` 之后在主线程里断言。
- 栈增长本身不用测, 不溢出、结果正确就行。想亲眼看的话, 在一个不内联的普通函数里取局部变量的地址: 原型里 10 万层的增长是 `-O0` 约 2.8 KB、`-O2` 约 0.3 KB。协程的局部变量在堆上, 从协程体里取地址量不出来。

`try_unittest.cpp`:

- `Try(Task<int>)`: 产出是 Ok, `value()` 等于任务的产出。
- `Try(Task<void>)`: 产出是 Ok。
- 任务抛 `std::runtime_error`: 产出是 Err, `std::rethrow_exception(r.error())` 接到的类型和 `what()` 都不变。
- 任务抛 `CancelledError(CancelReason::ABORT)`: 产出是 Err, 重抛接到的就是它, `reason()` 是 `ABORT`。
- 任务产出只可移动的类型 (`std::unique_ptr<int>`): Ok, `value()` 里的指针能用。

`task.md` 第 7 节的三个反向检查:

- 同一个 `Task` 被 `co_await` 两次、协程运行期间销毁它的 `Task`: debug 构建下进程中止。GTest 里不方便断言"进程中止", 写成单独的可执行文件或者用 `EXPECT_DEATH` 都行, 在验收记录里写明用了哪种、输出是什么。
- 函数体里没有任何 `co_` 关键字的 `Task<void>` 函数: 临时加一个, 确认编译有 `-Wreturn-type` 警告, 然后删掉。不提交。

### 5.8 链接检查

`zenio_api_compile_check` 只编译不链接, 查不出共享库缺符号。再加一个链接并运行的检查:

`tests/link_check/CMakeLists.txt`:

```cmake
add_executable(zenio_api_link_check api_link_check.cpp)

# 只链接共享库 zenio, 不链接 zenio_obj: 要查的就是库外需要的符号都导出了 (S31)
target_link_libraries(zenio_api_link_check PRIVATE GTest::gtest_main zenio::zenio)

target_include_directories(zenio_api_link_check PRIVATE
        ${CMAKE_SOURCE_DIR}/src
        ${CMAKE_BINARY_DIR}/src
)

gtest_discover_tests(zenio_api_link_check
        DISCOVERY_MODE POST_BUILD
        PROPERTIES TIMEOUT 60
)
```

`api_link_check.cpp`:

- 只包含 `<zenio/zenio.h>`, 不包含任何 `zenio/detail/` 下的头文件。
- 用 GTest。每个用例走一遍目前已经实现、并且会用到库内符号的 API:
  - `Builder::CurrentThread().EnableAll().Build()`, `Runtime::BlockOn` 一个多层嵌套的 `Task<int>` (中间 `co_await Yield()`), 检查产出。
  - `BlockOn` 一个用 `Try` 包住抛异常任务的协程, 检查拿到 Err。
  - 协程里 `Handle::Current()`、`TryCurrent()`, 和 `rt.handle()` 用 `operator==` 比较。
  - `Handle::Enter()` 的作用域内外。
- 以后的里程碑往这个文件里加用例, 每实现一批 API 就把它们接到链接检查上。

`tests/CMakeLists.txt` 加一行 `add_subdirectory(link_check)`。它不在 `tests/zenio/` 下, 那里的 `*.cpp` 会被收进 `zenio_unittest`。

## 8. 实现偏差

实现时没有记, 下面两条是审查时由设计会话补记的。

1. **`docs/design/build.md` 第 4 到 6 节改了写法**: 构建目录固定成 `build-debug`、`build-release`、`build-asan`、`build-tsan` 四个; 编译器统一成 Homebrew LLVM。这不在任务书的范围内。
   - 原因: 编译器的规则是用户给的; 构建目录是同一批改动里定的。
   - 处理: 编译器规则登记为 S32, 保留。原文里"TSAN 在 Apple Clang 上不支持 arm64 macOS"与实测不符, 已删。
   - 同步修改: design/build.md 第 4 到 6 节, design.md 1.4 的 S32。

2. **两个 death 用例只在 Debug 注册。** `Task.DeathDoubleCoawaitAborts`、`Task.DeathDestroyRunningTaskAborts` 放在 `#if !defined(NDEBUG)` 里, 用 `EXPECT_DEATH`。
   - 原因: Release 下断言不生效, 用例没有意义。
   - 实际输出: Debug 下两个用例都通过, 各约 18 毫秒; 所以 Debug、ASAN 是 90 项, Release 是 88 项。
   - 同步修改: 无。
